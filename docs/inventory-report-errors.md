# 上传库存幂等登记与错误恢复

上传文件身份由 namespace、repoType、完整 repo、path、SHA256 确定，大小必须一致。文件已存在时查询、核对并复用 ID，不再依赖 `ON DUPLICATE KEY UPDATE id=id` 跳过重复文件。首次插入并发冲突时回滚整个报告事务并重新执行（最多三次），避免在失败事务或旧快照里继续读写；代次、水位与持有关系仍原子提交。v2 报告和兼容旧库存入口使用同一身份登记实现。

报告响应保留 `error`，新增 `code`，已明确分类时带 `retryable`：

| 情况 | HTTP | 自动重试 |
| --- | --- | --- |
| 报告格式错误 | 400 | 否 |
| 身份、代次、内容冲突 | 409 | 否 |
| 有限事务重开后仍重复键 | 409 | 否，需要核对数据库 |
| 数据库死锁、锁等待超时、网络超时 | 503 | 是 |
| 未分类服务错误 | 500 | 客户端有限预算 |

新版 Speed 对明确冲突立即停止对应报告；未分类错误最多自动尝试八次。网络错误、408/429/502/503/504 继续退避，最大间隔约 256 秒加随机抖动。新响应优先使用 retryable；旧 Scheduler 无结构化字段时，409 中的数据库 1205/1213 按临时错误重试，1062 按明确冲突停止，其余旧 409 使用八次未知错误预算，不能视为成功。旧 Speed 不识别停止机制，需要单独升级 Speed 才能停止无限重试。

停止状态在 Speed 本地 outbox 持久保存，固定报告和后续本地变化不会被清除；普通事件、重启、重连和同代次查询不解锁。状态成功回报后不反复写 needs_attention。单仓增量冲突只停止该仓库 Entry，其他仓库继续上报；节点级停止仅用于完整基线。其他节点和本地上传发布不受队列停止影响。

不增加定时恢复查询。Speed 仅在启动、重连时执行原有 session 检查：首次接入可建立首个基线，已完成基线不重新盘点，未完成任务可继续，同代次失败停止不解除。普通心跳和本地变化不创建新的全量对账。失败的报告保留，等待下一次明确的全量对账。

人工发起全量对账时 Scheduler 通知 Speed 一次；发送失败只持久记录需处理状态和错误，不后台补发，也不因 Scheduler 重启重新推送。任务仍可在 Speed 启动/重连时读取。用户再次人工发起时创建新代次重试。Scheduler 内部原有有限事务重试不变，既有临时传输错误仍按退避处理。

修复原因后通过现有显式对账产生新代次恢复；重建成功后基线之后的新变化继续上报。不要删除 outbox 或库存记录来假装成功。本次没有数据库迁移，也没有证明现场数据库拒绝旧 SQL 的底层原因。

本地验证使用 SQLite/HTTP 故障注入和隔离 MySQL。可设置 `INVENTORY_TEST_DSN` 运行 `TestMySQLInventoryIdempotencyConcurrencyAndRollback`；仅允许 loopback TCP，测试创建并清理唯一命名的临时库，不能指向业务数据库。MySQL 通过不等于现场 DingoDB 已验收。
